## Тестлэгдэх функц

`POST /registrations` — оюутныг хичээлд бүртгэх. `server.js` дотор шалгалтууд дараах дарааллаар хийгддэг:

1. `studentID` эсвэл `courseID` дутуу → 400 `ERROR_BAD_REQUEST` (буруу JSON бол 400 `ERROR_BAD_JSON`)
2. Оюутан байхгүй → 200 `ERROR_NO_STUDENT`
3. Оюутан идэвхгүй → 200 `ERROR_INACTIVE_STUDENT`
4. Хичээл байхгүй → 200 `ERROR_NO_COURSE`
5. Урьдач нөхцөл дутуу → 200 `ERROR_PREREQUISITES` ба `missing` жагсаалт
6. Бүгд зөв → 201 `OK` ба `registrationID`

## Тест дизайн

### Сонголтууд ба төлөөлөх утгууд

| Сонголт | Эквивалент анги | Төлөөлөх утга |
|---|---|---|
| Оюутны төлөв | идэвхтэй | `status: "active"` |
| | идэвхгүй | `status: "inactive"` |
| | байхгүй | PUT хийгээгүй ID |
| Хичээл | байгаа | PUT хийсэн courseID |
| | байхгүй | PUT хийгээгүй ID |
| Оюутны үзсэн хичээл ба урьдач нөхцөл | бүгд хангана | `coursesTaken: ["CS201"]`, урьдач `["CS201"]` |
| | огт хангахгүй | `coursesTaken: []`, урьдач `["CS201"]` |
| | зарим нь хангана | `coursesTaken: ["CS201"]`, урьдач `["CS201","CS202"]` |
| Хичээлийн урьдач нөхцөл | байхгүй | `prerequisites: []` |
| Хүсэлтийн формат | зөв | `studentID` ба `courseID` хоёулаа байгаа |
| | талбар дутуу | `courseID` эсвэл `studentID` байхгүй |
| | буруу JSON | `{bad json` |

### Спецификацийн хүснэгт

| № | Спецификаци | Хүлээгдэх статус | Хүлээгдэх result |
|---|---|---|---|
| T1 | Happy path: идэвхтэй оюутан, урьдач хангасан | 201 | `OK` (`registrationID` тоо) |
| T2 | Оюутан байхгүй | 200 | `ERROR_NO_STUDENT` |
| T3 | Идэвхгүй оюутан | 200 | `ERROR_INACTIVE_STUDENT` |
| T4 | Хичээл байхгүй | 200 | `ERROR_NO_COURSE` |
| T5 | Урьдач нөхцөл огт үзээгүй | 200 | `ERROR_PREREQUISITES`, missing = [CS201] |
| T6 | Урьдач зарим нь дутуу | 200 | `ERROR_PREREQUISITES`, missing = [CS202] (зөвхөн дутуу нь) |
| T7 | Давхар алдаа: оюутан ба хичээл хоёулаа байхгүй | 200 | `ERROR_NO_STUDENT` (оюутны шалгалт түрүүлнэ) |
| T8 | Давхар алдаа: идэвхгүй оюутан + урьдач дутуу | 200 | `ERROR_INACTIVE_STUDENT` (төлвийн шалгалт урьдачаас түрүүлнэ) |
| T9 | Хязгаар: урьдач нөхцөлгүй хичээл + хоосон `coursesTaken` | 201 | `OK` |
| T10 | Хязгаар: `courseID` талбар дутуу | 400 | `ERROR_BAD_REQUEST` |
| T11 | Хязгаар: `studentID` талбар дутуу | 400 | `ERROR_BAD_REQUEST` |
| T12 | Хязгаар: буруу JSON | 400 | `ERROR_BAD_JSON` |

Тест бүр бие даасан: өөрийн `setup` PUT хүсэлтүүдийг (өвөрмөц ID-тай, ж: `T3_S`, `T3_C`) өөрөө хийдэг. `registrationID`-ийн яг утгыг шалгадаггүй, зөвхөн тоо мөн эсэхийг шалгана.

## Newman-ы үр дүн

Тестийн тоо: **12 тест кейс, 27 assertion** (`results/newman-pass.txt`-ийн *assertions executed* = 27).

| Ажиллуулалт | Файл | requests failed | assertions executed / failed | Exit code |
|---|---|---|---|---|
| PASS | `results/newman-pass.txt` | 0 | 27 / 0 | **0** |
| FAIL | `results/newman-fail.txt` | 0 | 27 / 1 | **1** |
| DOWN | `results/newman-down.txt` | 26 | 27 / 27 | **1** |

- **PASS:** `lab05-collection.json`-ийг сервер ажиллаж байхад ажиллуулав. Бүх assertion амжилттай.
- **FAIL:** `lab05-collection-fail.json`-д T1-ийн статусын oracle-ийг зориуд 201-ийн оронд 200 болгов. Сервер 201 буцаасан тул 1 assertion унаж, exit code 1 болсон. Энэ нь CI quality gate-ийн зарчим: нэг oracle унавал pipeline зогсоно. Үндсэн `lab05-collection.json` зөв хэвээр.
- **DOWN:** Серверийг Ctrl+C-ээр унтрааж ажиллуулав. Гаралтад `connect ECONNREFUSED 127.0.0.1:3000` мөр гарсан, exit code 1.

**Интерфейсийн алдаа ба oracle-ийн алдааны ялгаа:** DOWN-д серверт холбогдож чадаагүй (ECONNREFUSED) тул хариу ирээгүй, шалгах зүйл байгаагүй — энэ нь интерфейсийн алдаа; харин FAIL-д хариу ирсэн боловч хүлээгдэж буй утгатай таарээгүй — энэ нь oracle-ийн алдаа.

## Дүгнэлт

Дизайны 5 алхмаас хамгийн их бодол шаардсан нь "сонголтуудыг тодорхойлж, төлөөлөх утгыг сонгох" алхам байлаа, учир нь оюутны төлөв, үзсэн хичээл, урьдач нөхцөл гурав хоорондоо уялдаж байгаа. Зарим хослол бодитоор боломжгүй байсан: жишээлбэл оюутан байхгүй бол түүний үзсэн хичээлийн талаар ярих боломжгүй, мөн хичээл байхгүй бол урьдач нөхцөл гэж үгүй. Давхар алдааны хослолуудаар (T7, T8) серверийн шалгалтын дараалал нь оюутан, төлөв, хичээл, урьдач гэсэн дарааллаар явдгийг баталгаажуулсан. Урьдач нөхцөл зарим нь дутуу үед `missing` жагсаалт зөвхөн дутуу хичээлийг агуулдгийг T6 шалгасан. Тест бүр өөрийн setup-аа хийдэг тул дарааллаас хамаарахгүй, давтан ажиллуулахад аюулгүй байсан. `registrationID` сервер ажиллах хугацаанд нэмэгддэг тул яг утгыг нь биш, зөвхөн тоо мөн эсэхийг шалгасан нь тестийг тогтвортой болгосон. Миний 12 тест ямар ч согог илрүүлээгүй, бүгд хүлээсэн үр дүнтэй таарсан. Гэхдээ `server.js`-ийг уншихад нэг оюутныг нэг хичээлд хоёр удаа бүртгэхийг сервер хаадаггүй (хоёр удаа 201 буцаана) нь боломжит согог бөгөөд үүнийг би тестлээгүй байна. FAIL ажиллуулалт нь нэг буруу oracle exit code 1 үүсгэж, автомат шалгалтыг зогсоодгийг харуулсан. DOWN ажиллуулалт нь серверийн холболтын алдаа ба oracle-ийн алдааг ялгах хэрэгтэйг харуулсан. Дараагийн удаа давхар бүртгэлийн тест нэмж, `GET /registrations`-аар бүртгэл үнэхээр хадгалагдсаныг шалгах байсан.
